Fraud stopped before the money leaves.

A classifier for mobile-money transfers, trained on 6.36 million simulated PaySim transactions and evaluated the way a fraud-operations team would: hyperparameters tuned only on earlier data, a strict time-based holdout, walk-forward validation across four later windows, calibrated probabilities and a threshold chosen from the cost of each kind of mistake. The result is stated in money and in honest customers frozen.

The trained trees and calibration curve are re-implemented in pure Python for this always-on demo (src/export_model_json.py and api/score.py) and checked against the scikit-learn and XGBoost model on 20,000 fixed-seed transactions, agreeing to within floating-point precision. Not a mock and not a lookup table. The function loads the current export from the repository, so it always scores with the latest trained version.

Amounts are in PaySim's simulated currency units. The model sees the amount and four features derived from these five fields.

The score, the decision at the shipped operating threshold, and the share of the sender's balance moved will appear here.

Framing

A precision problem, not an accuracy problem.

PaySim's fraud rate is 0.13%. A model that predicts "not fraud" every time scores 99.87% accuracy and catches nothing.

What a fraud flag costs

In mobile money a flag usually freezes the customer's funds. Every false alarm locks an honest customer out of their own money; every missed fraud is a direct loss. A fraud-operations team needs three answers: how much fraud value the model stops, how many honest customers it freezes to do so, and whether that holds up as time passes.

What this project adds

PaySim is a common tutorial dataset, so the contribution is the evaluation rigour: a time-based split, hyperparameters tuned on earlier windows only, calibration on the latest training hours, a cost-sensitive threshold, walk-forward validation, drift monitoring and a five-model comparison in the notebook. Precision and recall are measured on data the model never saw, and the result is put in money.

Build

Seven stages, each answering one open question.

The order matters: each stage was run only once the previous one had an answer, and the fix at stage six came from using the dashboard, not from the metrics.

01

Baseline model

Can a model tell fraud apart from legitimate transactions at all? src/train.py

02

Hyperparameter tuning

40 Optuna trials scored only on windows that end before every reporting window, so no tuning row is used to report a result. The model ships with the tree count early stopping chose. src/tune.py

03

Walk-forward validation

Does it hold up on more than one train/test split? src/validate.py

04

Drift monitoring

How would we know if the model started drifting in production? src/monitoring.py

05

Dashboard

How does someone without Python use this? dashboard/app.py

06

Feature fix

Live-testing the dashboard found the model flagging legitimate account closures as 100% fraud, traced to raw balance columns that were then removed from the inputs. The fix is partial: a fully consistent full drain still scores 90.2%, because the drain ratio carries the same signal.

07

Diagnostics

Does one feature dominate the decisions, and where is the real precision, recall and cost trade-off? src/explain.py

Limits

What this result does not show.

Stated so a reader can weigh the figures rather than take them on trust. The model card in the repository goes further.

  • The threshold is a business choice, and it drifts. On the holdout the cost-optimal cut-off (0.8852) and a 0.5 cut-off make the same decisions, but across the walk-forward folds the cost-optimal threshold ranged from 0.021 to 1.00, and the fold with the lowest one reached only 88.1% precision. The near-perfect PR-AUC hides that no single fixed threshold is clearly right across the whole horizon. A deployment would revisit it periodically.
  • Destination-balance blind spot. The model cannot see whether the destination account's balance was updated consistently, because PaySim's CASH_OUT type does not strictly enforce destination-side accounting. A rule-based patch was tested on an earlier version and rejected because it multiplied false alarms on the training period.
  • Simulated data. PaySim reproduces the balance patterns of one mobile-money operator's logs, not the operator's live traffic. The headline precision depends on fraud being 2.1% of the holdout window; at the simulator's overall rate of 0.13% the same model would raise more false alarms per fraud caught.
  • A full drain scores high. Emptying the sender's account is the documented fraud pattern in PaySim, so a legitimate account closure can still be flagged: in the model card's test, moving 99% of a balance scores 0.0000% and moving 100% scores 90.24%. The score is a step, not a slope, so small changes to the sender's balances can swing it sharply. The scorer above says so when a flagged transaction empties the account.
