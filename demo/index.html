Portfolio Case Study

Mobile-money fraud detection,
evaluated the way a risk team would

XGBoost classifier on 6.3M simulated PaySim mobile-money transactions. Hyperparameters tuned only on earlier data, a time-based holdout, walk-forward validation across 4 later windows, calibrated probabilities and a cost-based threshold. It stops 99.99% of holdout fraud value, against 1.1% for the simulator's built-in rule.

Why this is a precision problem, not an accuracy problem

PaySim's fraud rate is 0.13%. A model that predicts "not fraud" every single time scores 99.87% accuracy and catches nothing. Fraud-ops workflows freeze customer funds on a flag, so false positives carry real trust and regulatory cost. This project measures precision and recall on a strict time-based holdout, chooses the alert threshold from the cost of each kind of mistake, and puts the result in money: the value of fraud stopped and the number of honest customers frozen. PaySim is a common tutorial dataset; the contribution here isn't the dataset choice, it's the evaluation rigour: time-based split, calibration, cost-sensitive thresholds, and a five-model comparison on identical pipelines.

What this doesn't claim

Limitation 1: the threshold is a business choice, and it drifts

The cost-optimal cut-off (0.0123) catches one more fraud than a 0.5 cut-off but freezes 41 more honest customers, and it ranged from 0.017 to 0.89 across the walk-forward folds. The near-perfect PR-AUC hides that no single fixed threshold is clearly "correct" across the whole time horizon. A real deployment would need to revisit it periodically.

Limitation 2: destination-balance blind spot

The model can't see whether the destination account's balance was updated consistently, because PaySim's CASH_OUT type doesn't strictly enforce destination-side accounting. A rule-based patch for this was tested and rejected: on an earlier model version it produced 44,996 false alarms on the training split, up from 136. See MODEL_CARD.md.
